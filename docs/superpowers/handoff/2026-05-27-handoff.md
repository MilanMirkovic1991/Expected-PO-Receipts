## 5. **CRITICAL: Real DELMIAWORKS API Quirks** (vs. the original spec)

The original spec's section 9 listed open questions for the first DW call.
This is what we actually learned. **Treat this section as authoritative when
the spec or plan disagrees.**

### Server

- Base URL: `http://192.168.20.28:8080/WebAPI`
- Database: `IQORA`
- EPlantId: `13` (only one in this DB)
- Stack: Microsoft IIS 10.0, ASP.NET MVC 4 (legacy DW WebAPI)
- CORS: `Access-Control-Allow-Origin: *`, allows `AuthToken` header — frontend dev proxy is for convenience, not needed at runtime

### Endpoints that work

| Endpoint | What it actually returns | Notes |
|---|---|---|
| `POST /User/Login` | `{ AuthToken, UserName }` (top-level — no `.data` wrapper) | The token format is `KERFU...|<guid>` |
| `GET /POReceiving/PO/POs/0?filter=(EplantId.eq~13~)&pageSize=N` | `{ data: [PO summaries] }` — **header only**, no nested PODetails | Use this to list which POs exist for the EPlant |
| `GET /POReceiving/PO/PurchaseOrder/0?poNo=X` | `{ data: { ... Status, PODetails: [{ ... POReleases: [...] }] } }` | The **only** endpoint that gives the full nested tree. PODetails have ItemNo/ItemClass/ItemRev/ArInvtId but NO Description. |
| `GET /POReceiving/PO/POReceipts/0?poDetailId=N` | `{ data: [receipts] }` | Used to subtract received qty from a release |
| `GET /AccountsPayable/VendorMaintenance/Vendors/0?pageSize=N` | `{ data: [vendors] }` with `Id`, `VendorNo`, `Company` | `Company` is the name — not `VendorName` |
| `GET /Workforce/EmployeeMaintenance/PREmployees/0?pageSize=N` | `{ data: [{ Id, EmpNo, FirstName, LastName, PRDepartment, PkHide, ... }] }` | **PR_EMP** as the user asked. No `UserName` or `Email` columns. |
| `GET /Manufacturing/Inventory/Inventory/{arInvtId}` | `{ data: { Id, ItemNo, Rev, Description, Class, UOM } }` | Used for description enrichment |

### Endpoints that **DON'T** work as the docs suggest

| Endpoint | Issue | What we do instead |
|---|---|---|
| `GET /POReceiving/PO/POReleaseItems/0` | Returns **HTTP 500** — controller signature is `POReleaseItems(Int64 poLineItemId)` and id=0 fails the non-nullable check. The spec assumed this was a list endpoint. It isn't. | Walk `POs/0` → `PurchaseOrder/0?poNo=X` and harvest `PODetails[].POReleases[]` (see `dwClient/poReleases.ts`) |
| `GET /TimeAttendance/Employees/TeamMember/0` | Returns `{"data": null}` | Switched to PREmployees |
| `GET /TimeAttendance/Employees/Employee/0` | Returns `{"data": null}` | Same — these "by id" endpoints don't act as list endpoints even with filter |
| `GET /TimeAttendance/Employees/TAEmployees/0?showHidden=false` | Returns `{"data": null}` | Same |
| `GET /POReceiving/PO/PO/{id}` | Returns flat header only — no nested PODetails | Used `/PurchaseOrder/0?poNo=X` instead |
| `GET /AccountsPayable/VendorMaintenance/Vendor/{id}?vendorId={id}` | Returns null for some valid ids in IQORA (didn't investigate) | Use the list endpoint + cache; lookup by id from cache |

### Response shape gotchas

- DW responses **sometimes** are `{ data: [...] }` and **sometimes** are bare arrays. `pickArray()` in `dwClient/shared.ts` handles both plus a few wrapper-key variants (`Items`, `Result`, etc.). Use `pickArray` for any list response — never the older `unwrap<any[]>` pattern.
- `unwrap<T>` is still fine for single-object responses (e.g., `CreatePOReceipt` reply).
- DW filter syntax `(field.op~value~&other.op~value2~)` works for AND. URL-encode the whole filter param. Only `gte` is supported for dates — we trim the upper bound client-side.
- Dates from DW look like `2026-05-27T00:00:00` (no timezone). We treat them as local time strings and slice to `YYYY-MM-DD`.

### Status filter for POs

When walking POs we skip headers whose `Status` (UPPER + trim) is in:
`{ CLOSED, CANCELLED, CANCELED, VOID, VOIDED, DELETED }`. `APPROVED` and `OPEN` (and empty) all pass through.

### PR_EMP and the missing login link

PR_EMP has no `UserName` or `Email` columns. The mapping between a logged-in
DW security user and a payroll employee record lives in tables we cannot
reach via the public WebAPI (`IQMS_USER` or similar). Consequences:

1. **No email notifications.** `assigned_to_email` is always empty. The
   mailer is wired but will never fire.
2. **No per-user task filtering.** `GET /api/tasks` returns every open task
   regardless of who is signed in. The Receiving page shows assignee name +
   badge so the worker can identify their tasks visually. This is documented
   in code (`routes/tasks.ts`) and in `db/queries/tasks.ts::listAllOpen()`.
3. **No "only assignee can receive" check.** Any signed-in user can receive
   any open item. Once we can map session.username → PR_EMP.Id, restore the
   `t.assigned_to_username !== req.session!.username` guard.

If the user later provides the SQL view or table that links security users
to PR_EMP, the simplest fix is a new dwClient method `findEmployeeByLogin`
and re-enable the guards.

### Idempotency & race notes (still good)

- `markReceived` uses an optimistic `UPDATE ... WHERE id = ? AND status = 'pending'` and returns `changes > 0`. If two requests race past the DW call, only one DB update lands; the loser gets `ITEM_ALREADY_RECEIVED`. There's still a narrow window where both could call DW and produce double receipts — documented in `taskService.ts:111`.
- `createTask` is atomic — `TaskQueries.insertWithItems` wraps both inserts in one SQLite transaction.

## 7. Open Items & Known Limitations

### High priority — verify with real DW before next change

1. **Employee dropdown shows PR_EMP** — switched from TeamMember to PREmployees
   in commit `0f3e87e`. User has not yet refreshed the browser to confirm. If
   the dropdown still empty, check backend log for `dw.employees.PREmployees: parsed`
   line and inspect the `rowCount`.
2. **Vendor column on POReleaseTable** — same commit. Should show "EMKA" for
   vendor 61465 on PO 6-1.
3. **End-to-end receive flow has never run against IQORA.** Steps in order:
   1. Create a task with at least one item
   2. Open the task in Receiving
   3. Fill Lot No, Qty, Location, Printer; click Receive
   4. Backend will call `CreatePOReceipt` → `PostPOReceiptAndUpdateMasterLabel` → `PrintPurchased`
   5. Expect one or more failures — verify endpoint shapes match (see open question #4)

### Medium — known-imperfect, would improve robustness

4. **`PostPOReceiptAndUpdateMasterLabel` response field for masterLabelId.**
   We assume `FgMultiId`. If wrong, label print fails (logged as warn, receipt
   still succeeds). Fix in `dwClient/poReceipts.ts:51`.
5. **`PrintPurchased` body shape.** We send `{ Qty: input.qty }`. Untested
   against real printer.
6. **Locations endpoint shape.** `dwClient/locations.ts` uses `LocCode`,
   `Description`, `ReceiveDesignator` field names — unverified on IQORA.
7. **`getDefaultRecvDesignator`** in `inventory.ts` returns null in tests.
   Probably never works on IQORA — the column might not be exposed, or might
   be named differently. Currently the UI shows "default" for missing values,
   which is acceptable.
8. **EPlants endpoint** (`/api/eplants?baseUrl=...`) — never called by the
   UI because EPlantId is hardcoded via env. If we add multi-plant support,
   verify the route works.

### Low / Future work

9. **PR_EMP ↔ DW security user mapping.** When discovered, restore per-user
   task filtering and the receive permission check.
10. **SMTP configuration.** Add real SMTP creds to `.env` and the system
    will start emailing — code already in place.
11. **`'failed'` status for items.** The schema has it; nothing sets it.
    Reserved for future retry workflows.
12. **Bulk receive.** Spec explicitly punted to v2 — workers receive one item
    at a time. UI is set up for that pattern.
13. **Multi-language UI.** Currently English only.
14. **More test coverage for routes** — `locations`, `printers`, `employees`,
    `notifications` routes have thin or no tests beyond smoke. The implementer
    flagged this during plan execution.
15. **`pageSize=1000` cap on PO summaries** in `poReleases.listOpenByPromiseDate`
    — logs a warning when reached; would need pagination for >1000 open POs.
16. **Receipts query is N+1** — one HTTP request per unique PODetail to get
    QtyReceived. Acceptable for tens to a few hundred items, but a date range
    with 500+ items will be slow. Possible improvement: parallelize with
    bigger concurrency window or cache receipts per-task.

### Cosmetic / nice-to-have

17. **Cancel task UI.** Backend supports it; frontend has no button yet.
18. **Edit task after generate.** Out of scope per spec.
19. **Show vendor on TaskCard** — currently only shows assignee. Vendor could
    summarize the task ("3 items from EMKA · 2 from ACME").

### Re-deriving the auth token for curl probes

The token from the running backend session is in any error log line under
`headers.AuthToken`. Or — login once via the app, then open DevTools →
Application → Cookies → copy `sessionId`, then hit `/api/auth/me` to
confirm.

To probe DW directly with `curl`:
```bash
TOKEN='<paste the AuthToken value>'
curl -s --max-time 10 -H "AuthToken: $TOKEN" "http://192.168.20.28:8080/WebAPI/<endpoint>" | head -c 2000
```
